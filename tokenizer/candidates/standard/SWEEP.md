## 9. Deviations, interpretations, and what was not done

- **G1 scope.** PLAN §4.3 defines G1 on 100% of dev *and test* documents. This run must not touch the test split, so G1 was run on dev_strict (836 documents) and dev_permissive (1,358) only. The test half of G1 belongs to the Stage 5 one-shot evaluation.
- **Size at which the selection rules are applied.** PLAN §3 states the rules without naming a vocabulary size. They were applied at **16k**, the size of the rank-1 standard recipe (and of ranks 2–5, 7). The per-size outcome is reported for every size at which both arms exist, and SWEEP.md §1 says whether it is the same everywhere.
- **Data-mix tie.** PLAN does not say what happens if both D2 and D3 qualify; the code would pick the larger overall gain. The case did not arise: at 16k only D2 qualifies, and at 32k neither does.
- **Reference for the A2/A3 rule.** 'Better than A1' is read as: A1 byte-level BPE with the chosen pre-tokenizer, same size, same data (D1).
- **G2 for superword pieces (A8).** harness.gate_g2 lists pieces with whitespace inside as untested; PLAN's 'shortest train chunk' procedure was written for SuperBPE. For a Unigram (Viterbi) encoder the isolated self-tokenization of the piece's own string is the exact reachability test (the PLAN §4.3 remedy argument), so A8's superword pieces were tested that way (sweep_lib.g2_superword) and count towards G2.
- **Pm pre-tokenizer differential (PLAN §1.3).** Stage 0 checked P1, P1r3 and P0 only. For Pm, the Python `regex` twin and the Oniguruma regex give identical pretokens on dev_strict, dev_permissive, ZWNJ-perturbed dev_strict and harakat-stripped dev_strict (0 differing documents; `pretok_differential_Pm.json`).
- **G4 procedure for SentencePiece.** SentencePiece stores `model_prefix` (a path) in the model file, so both trainings wrote to the same prefix. The first file was moved to `g4/` before the second training, and the two files were compared byte for byte.
- **A5 and G4.** HF UnigramTrainer (tokenizers 0.22.2) gave different files for two trainings with identical inputs at every size. In a pre-sweep probe on a 5% line sample this also happened with RAYON_NUM_THREADS=1 (same pieces, score noise ~4e-11, different piece order). On the full data the six pairs have the same piece set, but scores differ by up to 2.0e-4, the piece order (the ids) differs, and at 24k and 32k one dev_strict document each segments differently even after mapping ids by piece string (at 8k, 12k, 16k and 48k the segmentations agree). G4 was applied as written (byte-identical files), so all six A5 tokenizers fail it and are dropped. A canonicalising post-processing step (for example, sorting pieces by rounded score) is not part of the pre-registered A5; it was not built and would not remove the segmentation differences. Per-size diagnostic: stage1.json → g4_functional_diagnostic.
- **Special-token layout.** HF candidates: the 64 specials at ids 0..63. A1: 256 byte symbols at 64..319. A2: `<0xNN>` at 64..319. A5: `<unk>` at 64 and `<0xNN>` at 65..320; `<unk>` is never emitted, because HF Unigram needs an UNK lattice node before byte fallback. SentencePiece candidates: specials 0..63 as user-defined symbols, `\n` at 64, `<unk>` at 65, `<0xNN>` at 66..321. The total always equals the nominal size (a multiple of 64). A5 and the SentencePiece models therefore have 1–2 fewer learned pieces than a pure 64+256 layout.
- **A5 construction bug fixed during the run.** The first A5 build had no UNK piece. HF Unigram then raised 'unknown token but unk_id is missing' on a perturbed dev text with a character unseen in training (A5-P1-D1-48k failed in the robustness pass). The UNK piece was added (item above); every A5 in the results was trained with the fixed code, and the broken files were deleted. Workers still running the old in-memory code were kept off A5 through reserved lock files.
- **SentencePiece → HF export.** The task asks for an HF tokenizer.json for every tokenizer. For SentencePiece candidates this file is an export (sweep_lib.sp_to_hf_json): added tokens for `\n` and the specials, a Replace(' '→▁)+Prepend(▁) normalizer that reproduces SentencePiece's own whitespace escaping and dummy prefix (no Unicode normalisation, so it is not a normalizer in the PLAN §1.1 sense), and a Unigram or BPE model. Its equivalence with the native encoder was measured on dev (SWEEP.md §8). The native `sp.model` + newline wrapper stays the candidate's identity (PLAN §1.3). Unigram exports can differ on exact-score ties, e.g. '…………' = '………'+'…' vs '…'+'………'; SentencePiece sums scores in float32 and breaks such ties differently.
- **A2 alphabet.** PLAN/pilot built A2 with `limit_alphabet=1000`; here `limit_alphabet=None` (every character of train_D1 is kept). The normalised train_D1 has 251 distinct code points, so the two settings are equivalent. Every dev_strict character occurs in train_D1; only perturbed dev text (robustness pass) contains unseen characters.
- **R1 details.** Support is counted on train_D1 (the LM stage's training stream) for every tokenizer. For D2/D3 tokenizers it is also counted on their own mix. The leaf vs intermediate split needs a stored merge graph, so it is reported for the HF BPE candidates (A1, A2) only, not for SentencePiece BPE (A3).
- **Metrics scope.** All metrics are computed on dev_strict. dev_permissive was used only for G1, the SentencePiece-export equivalence test and the G2-remedy re-encoding check.
- **Timing.** Training times were measured with 2 threads per process while other agents kept the 8-thread CPU at 100% load. They are sanity numbers, not benchmarks, and entered no decision.
- **Code changes during the run.** After the reference tokenizer A1-P1-D1-16k was finished, run_sweep.py changed twice: the queue order (SentencePiece and HF jobs interleaved) and the lock take-over for reserved A5 configs. sweep_lib.py changed twice: the A5 UNK fix plus a vocabulary-size assertion, and later `handover_configs()`. None of these changes touches the A1/A2/SentencePiece training or evaluation path, so nothing was retrained. Tokenizers finished by workers started before an edit record older code hashes in their stage1.json/meta.json. The report checks each tokenizer's actual size against the nominal one (all match).
- **Not done in this run:** LM training (Stages 3–4), significance testing, anything on the test split, the Stage 2 candidates (A6 SuperBPE, A7 PickyBPE, A10 MinGram), MorphScore urd_arab (morphology is the SILVER report-only metric), and dev_permissive metric tables.
- **Hand-over tokenizers.** The pre-tokenizer rule (P1r3) and the data-mix rule (D2) were each measured against P1/D1, and PLAN's grid never crosses P1r3 with D2. To hand Stage 3 a gated rank-1/rank-6 tokenizer, A1-P1r3-D2 was trained at 8k/16k/32k after the rules had been applied, with the same code and gates (SWEEP.md §1.7). These three tokenizers entered no rule.
